💾OLTP vs OLAP

🔹 What is OLTP?

OLTP = Online Transaction Processing

  • Designed for day-to-day operations (insert, update, delete).
  • Handles lots of small transactions with high speed.
  • Focus is on data accuracy & concurrency.

✅ Examples:

  • ATM withdrawals.
  • E-commerce checkout.
  • Airline ticket booking.

👉 OLTP is like a cashier system in a store 🏪 — fast, handles many small transactions.

🔹 What is OLAP?

OLAP = Online Analytical Processing

  • Designed for analysis, reporting, decision-making.
  • Handles large volumes of historical data with complex queries.
  • Focus is on query speed & aggregation (not single transactions).

✅ Examples:

  • Sales trends across 5 years.
  • "Top 10 products sold last month by region."
  • Customer churn prediction.

👉 OLAP is like a business dashboard 📊 — slow to build, but shows big insights.

🔹 Key Differences: OLTP vs OLAP

🔹 Why Both Exist

  • OLTP came first → businesses needed systems to record transactions (banking, shopping, booking).
  • OLAP came later → managers needed to analyze trends to make decisions (how many people bought tickets last month?).

👉 OLTP = Run the business

👉 OLAP = Analyze the business

🔹 Real-World Example

Amazon OLTP:

Customer places an order → order stored in OLTP DB (fast, accurate).

Amazon OLAP:

Managers analyze "How many iPhones sold last quarter?" → Data comes from OLAP warehouse (Redshift/Snowflake).

✅ In one line:

  • OLTP = Fast, real-time transactions (operations).
  • OLAP = Deep, historical analysis (insights).

❄️Snowflake

Snowflake is a cloud-based Data Warehouse as a Service (DWaaS) platform. It allows companies to store, process, and analyze massive amounts of structured and semi-structured data (JSON, Parquet, Avro, etc.) without managing physical servers.

  • It runs entirely on cloud providers like AWS, Azure, and GCP — but Snowflake itself is not tied to any one of them.
  • Think of it as: 👉 A "Google Drive" for enterprise data storage + a super-fast SQL engine + elastic scaling.

❓ Why Snowflake Came into Existence

Traditional data warehouses (like Oracle, Teradata, Hadoop-based systems) had limitations:

  • Scalability issues → Hard to scale compute and storage separately. If you need more compute, you had to buy more storage too.
  • Concurrency problems → When many users query at the same time, performance drops.
  • Maintenance overhead → Traditional systems required hardware management, tuning, and lots of DBA work.
  • Semi-structured data support → JSON, XML, Parquet weren't easily handled in old warehouses.
  • Elasticity → Couldn't scale up/down quickly based on workload.

Snowflake was built (founded in 2012, launched in 2014) to solve these by:

  • Fully separating storage and compute
  • Being cloud-native (no hardware to manage)
  • Offering pay-as-you-go pricing
  • Handling structured + semi-structured data natively

⚡Apache Spark – Complete Notes

🔹 What is Apache Spark?

Apache Spark is an open-source, distributed data processing engine for big data. It handles batch processing, real-time streaming, machine learning, and graph workloads in one platform.

  • Provides APIs in Python (PySpark), Scala, Java, and R.
  • 100x faster than Hadoop MapReduce (due to in-memory processing).

👉 Think of Spark as a cluster brain that breaks big jobs into smaller tasks and runs them in parallel across many machines.

❓ Why Spark Came Into Existence

Before Spark, people used Hadoop MapReduce, but it had limitations:

  • Slow – wrote intermediate results to disk.
  • Batch-only – no real-time processing.
  • Complex – writing MapReduce code was hard.
  • Separate tools – SQL (Hive), ML (Mahout), Streaming (Storm).

👉 Spark was built (2009 at UC Berkeley, Apache project in 2013) to:

  • Be faster (in-memory).
  • Be easier (simple APIs).
  • Be unified (batch + streaming + ML + graph in one engine).

🏗️ Spark Architecture

Driver Program
→
Cluster Manager
→
Executors (Workers)
  • Driver Program – main controller (creates execution plan).
  • Cluster Manager – allocates resources (YARN, Kubernetes, Mesos, or Spark Standalone).
  • Executors (Workers) – do the actual task execution on distributed data.
  • RDD / DataFrame / Dataset – the data abstractions Spark provides to process data.

👉 Spark divides a job into tasks, distributes them to worker nodes, and then collects results back.

🔹 RDD (Resilient Distributed Dataset)

RDD is the fundamental data structure in Spark.

Definition: 👉 An RDD is a big list of data, split across many machines, with built-in fault tolerance.

✨ RDD Properties

Resilient

Fault-tolerant, can recover from node failures using lineage

Distributed

Data is divided across multiple machines in a cluster

Immutable

Once created, cannot be changed (only new RDDs can be made)

Lazy Evaluation

Transformations are only executed when an Action is called

Parallel Processing

Each task runs on different partitions of the RDD simultaneously

⚙️ RDD Operations

Transformations (lazy → return new RDDs)

Examples: map, filter, flatMap, reduceByKey.

Actions (trigger execution, return value or write output)

Examples: collect, count, first, saveAsTextFile.

👉 Example:

rdd = spark.sparkContext.parallelize([1, 2, 3, 4, 5]) rdd2 = rdd.map(lambda x: x * x) # Transformation print(rdd2.collect()) # Action → [1,4,9,16,25]

🔹 Evolution of Spark APIs

RDD (2010)

  • Low-level API, very flexible.
  • Best for unstructured data & custom logic.

DataFrame (2015)

  • Schema-based (rows + columns, like SQL tables).
  • Optimized by Catalyst optimizer.
  • Much faster for structured data.

Dataset (2016, Scala/Java only)

  • Type-safe (compiler checks schema).
  • Combines RDD flexibility + DataFrame optimizations.

👉 In Python → use RDD + DataFrame. 👉 In Scala/Java → can also use Dataset.

🔹 Spark Ecosystem

Spark Core

Base engine (RDDs, scheduling)

Spark SQL

DataFrames, SQL queries

Spark Streaming / Structured Streaming

Real-time data

MLlib

Machine learning library

GraphX

Graph computations

✅ Summary (Key Points for Notes)

  • Spark = fast, distributed, unified big data engine.
  • Came to replace slow & complex Hadoop MapReduce.
  • RDD = big list of data, split across machines, fault-tolerant.
  • Spark divides tasks across workers and processes them in parallel.
  • Evolution → RDD → DataFrame → Dataset (higher-level, optimized abstractions).
  • Ecosystem supports SQL, Streaming, ML, Graph workloads.

🌬️Apache Airflow – Complete Notes

🔹 What is Apache Airflow?

Apache Airflow is an open-source workflow orchestration tool used to programmatically author, schedule, and monitor data pipelines.

👉 In simple words: It's like a task manager for data pipelines — you tell Airflow what tasks to run and in what order, and it takes care of scheduling, execution, retries, and monitoring.

❓ Why Airflow Came Into Existence

Before Airflow (pre-2014), companies managed pipelines using cron jobs + shell scripts. But these had problems:

  • Hard to manage dependencies → e.g., Task B should run only after Task A finishes.
  • No monitoring → If a job failed at 2 AM, no one knew until morning.
  • Not scalable → Hard to manage hundreds of pipelines.
  • Lack of retry/recovery → If a job failed, you had to manually rerun it.

👉 Airflow was created at Airbnb in 2014 (later donated to Apache) to solve these:

  • Express workflows as code (Python).
  • Handle dependencies automatically.
  • Provide scheduling, retries, logging, and monitoring.
  • Be scalable across clusters.

🏗️ Apache Airflow Architecture

Scheduler
→
Executor
→
Workers
→
Metadata DB
→
Web UI

Scheduler

  • Decides what tasks need to run and when.
  • Sends tasks to the executor.

Executor

  • Runs the actual tasks.
  • Can run on Local, Celery, Kubernetes, or other backends.

Workers

Execute the tasks assigned by the executor.

Metadata Database (usually MySQL/Postgres)

Stores the state of all DAGs, tasks, schedules, etc.

Web UI

Monitor, trigger, retry, or debug workflows.

🔑 Core Concepts

DAG (Directed Acyclic Graph)

  • A collection of tasks with dependencies, defining your workflow.
  • Example: Task A → Task B → Task C.

Task

A single unit of work (e.g., run SQL, call API, trigger Spark job).

Operator

  • Pre-built templates for tasks.
  • Examples: PythonOperator, BashOperator, SparkSubmitOperator, SQLOperator.

Sensor

A special operator that waits for something to happen (e.g., a file arrival).

XComs (Cross-Communication)

Mechanism to pass small amounts of data between tasks.

⚙️ Example DAG (Python Code)

from airflow import DAG from airflow.operators.python import PythonOperator from datetime import datetime def hello_world(): print("Hello, Airflow!") with DAG("my_first_dag", start_date=datetime(2025, 1, 1), schedule_interval="@daily", catchup=False) as dag: task1 = PythonOperator( task_id="hello_task", python_callable=hello_world )

This defines a DAG with one task that prints "Hello, Airflow!" daily.

✨ Features of Apache Airflow

  • Workflows as code → pipelines written in Python.
  • Dynamic → DAGs can be generated programmatically.
  • Scalable → can run thousands of tasks across workers.
  • Monitoring UI → see DAG runs, logs, retries.
  • Retry & Alerting → failed tasks can retry or send email/Slack alerts.
  • Extensible → custom operators & plugins.

✅ Summary (For Notes)

  • Airflow = workflow orchestration tool for data pipelines.
  • Created because cron + scripts were hard to manage at scale.
  • Architecture = Scheduler, Executor, Workers, DB, Web UI.
  • Core concepts = DAG, Task, Operator, Sensor, XComs.
  • Features = code-as-pipelines, retries, monitoring, scalability, extensibility.

👉 Airflow is often used with Spark, Snowflake, Databricks, or BigQuery to orchestrate ETL/ELT pipelines.

📊Data Modeling

🔹 What is Data Modeling?

Data modeling is the process of defining how data will be structured, stored, and related inside a database or data warehouse. It's like creating a blueprint for data, similar to how an architect creates a blueprint for a building.

It tells us:

  • What entities (tables/objects) exist.
  • What attributes (columns/fields) they have.
  • How entities relate to each other (relationships, keys).
  • Rules/constraints (e.g., no duplicate emails, salary > 0).

🔹 Why Data Modeling Came into Existence?

Earlier, people just dumped data into flat files or basic tables, which caused:

  • Duplication (same data stored many times).
  • Inconsistencies (different formats, missing values).
  • Scalability issues (hard to query & maintain).

👉 To solve this, data modeling came up to bring standardization, clarity, and optimization to data storage & access.

🔹 Types of Data Models

Conceptual Data Model (High-level, business view)

  • Defines entities and relationships.
  • Example: Customer, Order, Product.

Logical Data Model (Detailed, but still independent of DB)

  • Defines attributes, primary keys, foreign keys.
  • Example: Customer (CustID, Name, Email).

Physical Data Model (Actual DB implementation)

  • Includes data types, indexes, constraints.
  • Example: CustID INT PRIMARY KEY, Email VARCHAR(100) UNIQUE.

🔹 Data Modeling Techniques

  • ER Diagrams (Entity-Relationship Models) → Common in OLTP databases.
  • Star Schema (Fact + Dimension tables) → Common in Data Warehouses (OLAP).
  • Snowflake Schema → Variant of star schema, with more normalization.
  • NoSQL Data Modeling → Denormalized, designed for scalability.

🔹 Benefits of Data Modeling

  • Reduces redundancy.
  • Improves query performance.
  • Easier maintenance.
  • Clear documentation for devs & analysts.
  • Supports data governance & compliance.

✅ In one line: Data modeling = Designing the structure of your data for accuracy, performance, and usability.

🔄Real-Time ETL vs ELT

⚡ Real-Time ETL

Here, ETL happens on the fly while data is moving (streaming pipelines). Instead of waiting hours for batch jobs, transformations are applied in real-time before loading.

Example Scenarios:

Fraud Detection in Banking 🏦

  • A customer swipes a card.
  • ETL pipeline (Kafka → Spark/Flink) extracts the transaction, transforms it (adds geo-location, checks limits), and loads into a fraud detection system instantly.

IoT Devices / Sensors 🌡️

  • Temperature or vehicle telematics data comes in continuously.
  • ETL cleans & standardizes data (e.g., units, missing values) before loading into a monitoring dashboard.

Stock Market Trading 📈

  • Prices update in milliseconds.
  • Real-time ETL applies normalization and feeds live dashboards or algo trading systems.
Apache Kafka Apache Spark Streaming Apache Flink AWS Kinesis Confluent

⚡ Real-Time ELT

Raw data is ingested immediately into a warehouse/lakehouse (like Snowflake, BigQuery, Databricks Delta Lake). Then near real-time transformations happen inside the warehouse using materialized views, streaming queries, dbt, or SQL pipelines.

Example Scenarios:

E-commerce Clickstream Analytics 🛒

🔄ETL vs ELT Decision Guide

🔹 Why Transform Before Loading (ETL)?

We do this when:

  • Target system is weak / expensive – Old data warehouses (Oracle, Teradata, SQL Server) had limited compute and storage was costly. So you clean & reduce data first, then load only the final version.

    Example: Bank transaction data → filter only last 7 years before loading.

  • Regulatory / compliance restrictions – Some industries (healthcare, finance) can't store raw PII data. So it must be masked, anonymized, or aggregated before going into the warehouse.

    Example: Mask patient names before storing in healthcare DW.

  • Performance optimization – If your queries don't need raw data, why store it? Store only the transformed final facts.

    Example: Instead of storing every IoT event, store "avg temperature per hour."

👉 ETL is like cooking food before putting it in the fridge 🍲 — you only keep the ready-to-eat version.

🔹 Why Transform After Loading (ELT)?

We do this when:

  • Target system is powerful & cheap – Cloud warehouses (Snowflake, BigQuery, Databricks) can scale infinitely and separate compute from storage. You can dump all raw data, no problem.

    Example: Load raw clickstream logs (billions of rows) into BigQuery, transform later with SQL.

  • Flexibility needed – Business requirements change. If you only stored transformed data (ETL), you'd lose the raw version. With ELT, you keep raw + transformed data, so you can reprocess anytime.

    Example: Today you need "sales per day." Tomorrow you may need "sales per region." Since raw data is there, you can transform again.

  • Faster development – You don't need to design transformations upfront. Load first, let analysts/scientists decide later.

    Example: Data scientists want raw logs for ML experiments.

👉 ELT is like putting groceries in the fridge 🥦🥩 — you keep raw stuff first, then cook whatever dish you need later.

🔹 Quick Comparison

Situation Choose
Warehouse is old/limited ETL
Warehouse is cloud-native & scalable ELT
Must comply with privacy rules (mask before storage) ETL
Want to keep raw + transformed data ELT
Data size small/medium ETL works fine
Data size huge (TB–PB) ELT is better

✅ In one line:

  • ETL = Used when warehouse is weak, storage is costly, or compliance forces you to clean first.
  • ELT = Used when warehouse is powerful, storage is cheap, and you want raw data flexibility.
